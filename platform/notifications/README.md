# Notification rewrite

This workspace replaces the Laravel Telegram daily/hourly digest pipeline without activating it. The implementation uses TypeScript, MariaDB durable state and the existing jobs/BullMQ adapter. All development verification uses fake AI/Telegram responses; no real message has been sent and no production notification ownership has moved.

```sh
npm run start -w @youtube-board/jobs -- notify:telegram:digest --period=hourly
npm run start -w @youtube-board/jobs -- notify:telegram:daily --dry-run
```

The default preview reads source/history and renders grounded extractive copy. It calls neither provider nor Telegram, creates no story/slot/dispatch/journal rows and does not suppress later delivery. It also respects existing durable dedup. The fixed-period aliases expose `notify.telegram.daily` and `notify.telegram.hourly` to the workflow registry. `--no-ai` explicitly uses extractive copy in execute mode; an absent AI key has the same fallback behavior as Laravel. `--force` is manual-only and needs its own gate; it cannot bypass a daily date claim, an already-attempted exact dispatch, an existing Laravel exact-post marker, or an uncertain delivery.

## Source and editorial lineage

Daily contexts select only `oneday`/`todate`, all-channel, undeleted rows, ordered by date and primary key. They retain the exact topic→named channel→channel event associations. TS oneday sources resolve their verified `ts_ai_runs` snapshot; legacy sources are bounded to channel AI rows not modified after the daily snapshot. Legacy todate sources use the same exact historical association requirement. An unsupported TS todate journal, ambiguous channel/title/ID, newer modified channel source or corrupt snapshot fails closed. Hourly contexts retain their matching published TS run and reject corrupt or inconsistent journals. Video IDs are byte-exact, and daily references must match the actual owning channel.

Channel tags remain the historical channel taxonomy, separate from the shared content vocabulary. Source enrichment, recommendation ordering, channel/group diversity, daily source-count ranking, hourly video-count ranking and incremental group metrics follow the Laravel workflow. At most 100 events and 500 videos per event are accepted. Exceeding source caps blocks the run rather than publishing an apparently complete subset. Missing hourly videos can make a post incomplete; daily missing/incorrectly owned references block projection.

Original event titles remain dedup/story identities. AI headlines are display-only and require membership in the exact supplied video IDs. Brief validation checks shape, named source membership and evidence membership, not factual entailment. Rejected or failed AI attempts retain `aiOutcome`, prompt hash, and available returned model/usage evidence. The writer sends Laravel's `EventNewsWriter` system prompt verbatim with the same pretty-printed `{events:[...]}` payload and parses the same `{items:[{title,headline,headline_video_ids,summary}]}` reply. A single batch request uses the maintained `sky-quality` alias, an 8,000 completion-token maximum and `TELEGRAM_OPENAI_TIMEOUT` (production Laravel: 270 s; bounded at 300 s) through the CLIProxyAPI gateways (`TELEGRAM_OPENAI_BASE_URL`/`OPENAI_BASE_URL`, then `OPENAI_GATEWAY_FALLBACK_BASE_URLS`); a gateway is skipped only when unreachable or persistently 429/5xx, and an outcome-unknown call is never resent. Provider failure or invalid output falls back to Laravel's grounded extractive copy (description, two named sources by group, shared keywords); with fewer than two named sources the post is incomplete. Daily events hydrate from the cached `urt_ai_date.data_json` topic map when it covers every event, otherwise from the same AiTopicProjector aggregation over the exact topic→channel-event references. The formatter escapes external text, retains at least two source links, uses an expandable report and enforces Telegram's 4,096 UTF-16 visible-unit limit.

## Durable state and bounded delivery

Migration `009_notifications.sql` creates missing Laravel-compatible `telegram_digest_stories` and `telegram_digest_dispatches`, plus `ts_notification_runs`, `ts_notification_attempts`, `ts_notification_slots` and append-only `ts_notification_resolutions` / `ts_notification_resolution_attempts`. Existing tables and history are preserved. Execute requires InnoDB state tables and an InnoDB shared Laravel `cache` table. Never drop history or clear a pending/uncertain claim to retry a message. Only the isolated test DB has received this migration.

Story matching preserves the recent 100-story / 72-hour default window, exact video overlap, title fingerprints, rolling observations, first-report threshold, 24-hour update cooldown, burst baseline and 72-hour resurfacing. Daily delivery fills at most one previously uncovered story per date. Hourly delivery caps at three messages. A successful send atomically updates durable dispatch/attempt/story state and the Laravel-compatible exact-post cache marker. A definite Telegram rejection releases only its pending claim and preserves the failed attempt. A timeout, network error, malformed response or otherwise uncertain outcome retains a durable claim and blocks future sends for that story across context changes. There is no automatic resend or claim expiry for uncertain delivery. Crashes between send and persistence similarly leave the pending claim fail-closed even beyond the ordinary 72-hour story matching window; explicit audited reconciliation is described below.

The runner shares one connection-owned `telegram.notifications` writer lock across both periods. It rechecks authorization and ownership before source mutations, provider requests and each send, journals the exact source and rendered posts, and re-reads the stable source hash before delivery. Normal view-count refreshes and ranking changes do not invalidate editorial content; a separate full snapshot hash retains the original counters and order. This is a last-observed consistency check, not a transaction over the independently updated source tables; the full source snapshot is linked to every attempt through its run. Final delivery bookkeeping is transactional. Existing Laravel exact-post database-cache entries are adopted using the explicitly configured cache prefix; adoption never keeps advancing an already-posted story's timestamp.

Scheduled execution uses durable ten-minute hourly slots in UTC and thirty-minute daily slots in Asia/Taipei. Daily slots operate from 09:00 through 20:59 Asia/Taipei: Laravel's `->between('9:00','21:00')` compares the second-precision `schedule:run` start with 21:00:00, so its 21:00 slot never fires in practice. `runtime/schedules.batch7.json` enqueues `*/10 * * * *` (hourly) and `0,30 9-20 * * *` (daily), the first minute of each Laravel slot. Missing/incomplete data may be reconsidered in a later slot. Nothing installs or enables a recurring schedule automatically.

## Operator gates

Actual execution requires `--execute`, `TS_INGESTION_ENABLED=true`, exact entries in `TS_INGESTION_OWNERS`, `TS_NOTIFICATION_ENABLED=true`, `TELEGRAM_DIGEST_ENABLED=true`, and configured Telegram credentials. Scheduled execution also requires the existing scheduler gate. Production additionally requires `TS_NOTIFICATION_LEGACY_DEDUP_STORE=database`, the existing production enable and exact write allowlist, `TS_NOTIFICATION_LARAVEL_STOPPED=true`, `TS_NOTIFICATION_HISTORY_VERIFIED=true`, and an explicitly configured `TS_LARAVEL_CACHE_PREFIX` (including explicitly empty when that is correct). These are operator attestations, not actions that stop writers or migrate history. The Laravel scheduler uses its own mutex, so a TS lock alone cannot establish handoff.

The actual Laravel notification dedup store is `services.telegram.dedup_store` / `TELEGRAM_DEDUP_STORE` (default `database`), independent of the application’s `CACHE_STORE=file`. Verify the notification-specific store. The current TS adapter requires Laravel’s notification database cache to use the same database connection and the default `cache` table; verify `DB_CACHE_CONNECTION`, `DB_CACHE_TABLE=cache` and the exact prefix against approved runtime configuration. The mere presence or absence of cache rows cannot establish that configuration. File/Redis overrides are explicitly unsupported until a reviewed export/import preserves their keys; switching the cache driver would discard the required evidence and is not a valid handoff. An explicitly empty prefix is valid only when verified against that store.

Before an approved handoff, stop both Laravel notification schedules/manual entry points, back up and verify stories, dispatches and the shared database cache, review any pending/uncertain records, and verify the exact bot/channel through approved runtime configuration. Do not print or commit bot tokens, channel credentials or gateway keys. Runtime secrets stay in Dokploy. Migration and notification activation require a separate production approval; the rewrite instruction does not authorize a real message.

`TS_NOTIFICATION_FORCE_ENABLED=true` additionally allows explicit manual `--force`; force is rejected for scheduled execution. Default notification configuration remains disabled. Notification AI uses `TELEGRAM_OPENAI_*` with the existing gateway/key fallback and the `sky-quality` alias, preserving the separate Laravel client path.

## Audited recovery and rollback readiness

```sh
npm run start -w @youtube-board/jobs -- notify:telegram:readiness
npm run start -w @youtube-board/jobs -- notify:telegram:resolve --dispatch-key=SHA256 --outcome=not-sent --operator=OPERATOR --evidence="Reviewed channel history and confirmed no delivery"
```

Readiness is read-only and fails the CLI exit status while any pending/uncertain dispatch exists. It must pass before rollback to Laravel: Laravel hourly delivery does not read the TS uncertain-dispatch table, so resuming it while unresolved claims exist could resend a message. Keep both notification writers stopped until the uncertainty is resolved.

Resolution defaults to preview and performs no HTTP. After independently inspecting the intended Telegram channel, an operator may explicitly choose `sent` or `not-sent`, supply a non-secret evidence reference and operator identifier, and add `--execute`. A `sent` resolution also requires `--sent-at=YYYY-MM-DDTHH:MM:SSZ`; it must be after the original attempt and not in the future. It restores the original journalled video/channel snapshot, not observations accumulated while delivery was uncertain. Missing original snapshot blocks confirmed-send resolution instead of inventing coverage. Legacy uncertain records without that snapshot require a separately reviewed historical repair.

Execute resolution requires the exact owner/production allowlist `notify.telegram.reconcile`, normal execution gates, and `TS_NOTIFICATION_RECONCILE_ENABLED=true`; production additionally requires the stopped-Laravel/history-verified attestations, the database notification-dedup store attestation, and an explicitly configured cache prefix. It can run while message delivery itself is disabled. Resolution is manual-only and cannot be scheduled or queued through the public workflow registry. It atomically appends the previous dispatch state, outcome, operator and evidence to `ts_notification_resolutions`, then marks confirmed delivery or releases a confirmed-not-sent claim. Confirmed-send resolution also writes the exact Laravel seen marker in the same transaction, from the original journalled context and title, and refuses inconsistent snapshot identities. The marker expires three days after the operator-confirmed send time; resolving older delivery does not extend its original dedup window. Confirmed-not-sent resolution writes no marker. Original attempt records are never deleted or rewritten to hide uncertainty. `ts_notification_resolution_attempts` links the exact unresolved attempt to its append-only resolution; confirmed-send recovery requires a unique unresolved attempt with the same message hash, and re-hashes the stored rendered post. `--force` is not a recovery substitute.

The separate Telegram provider accepts HTTPS or explicit loopback/private-IP HTTP gateways, preserving the deployed Docker-host gateway. HTTP to arbitrary public hosts is rejected. No external endpoint is contacted by previews or maintenance commands.

Latest verification after two actual Opus reviews: **35 notification tests (23 real MariaDB, 12 offline)** and **3 CLI tests**, with both workspace typechecks passing. Regressions include counter-only drift, UTC state, PHP fingerprint parity, all-table preview checks, daily uncertainty, multi-post interruption, send/commit failures, original-snapshot reconciliation and later-slot catchup. No production readiness claim follows from these local results.

The second review also moved batch dedup before story observation, preventing a smaller title variant from replacing the representative burst baseline. Run journals record delivery phase and the last observed send outcome, including pre-send interruptions and persistence failures. Unresolved stories remain protected outside the ordinary matching window.


## Laravel shared-cache handoff protocol (round 3)

The Laravel source is authoritative: `routes/console.php` uses the fixed `config/app.php` UTC timezone for hourly scheduling; daily uses Asia/Taipei. `TelegramScheduleSlotGate` calls database-cache `add` with the configured cache prefix and:

- Hourly key `tg:schedule:hourly:<UTC YYYYMMDD>:<floor(UTC minutes / 10)>`, TTL 15 minutes.
- Daily key `tg:schedule:daily:<Taipei YYYYMMDD>:<floor(Taipei minutes / 30)>`, TTL 35 minutes.
- Laravel stores PHP `serialize(true)` (`b:1;`) and a Unix-second expiration. Its `DatabaseStore::add` rejects any non-null unexpired value before `insertOrIgnore`.

Both manual and scheduled TS execution claim the compatible slot before source/provider work and renew/recheck it before each send. TS uses a valid PHP-serialized string containing its run UUID; Laravel sees a non-null claim and skips that slot. TS exempts a claim from foreign-activity checks only when the exact marker UUID resolves to a run journal for that period. Claim acquisition uses insert-if-absent or a value-and-expiration compare-and-swap on a verified TS owner, never overwriting an observed Laravel/unknown owner. Scheduled TS's durable slot still prevents repeated ticks; a manual retry after a definite rejection can reuse a verified TS slot.

Before claiming and again immediately before a send, TS checks both hourly and daily candidate slots from the previous 30 minutes, the current slot and the next slot. The next-slot check covers modest boundary/clock skew, not arbitrary clock drift; synchronized host clocks remain required. Unexpired unknown claims, or retained expired claims whose `expiration - documented TTL` indicates activity in that window, block execution with `notification_legacy_schedule_activity`. Prefix matching uses exact generated keys, not a LIKE pattern. A `b:1;` value identifies the Laravel protocol, not a cryptographic writer identity; a skipped/no-source Laravel schedule can also leave that value, so this is deliberately a conservative recent-activity refusal. TS-owned claims do not cause a 30-minute self-lockout.

After confirmed delivery, the transaction writes `<prefix>tg:digest:<period>:<contextKey>:<md5(original title)>` as `b:1;`, expiring no earlier than three days after delivery. The original title uses PHP’s ASCII-default `trim()` behavior; NBSP and fullwidth spaces remain significant in its MD5 identity. Context windows remain source Taipei strings (`h:YYYY-MM-DD HH:mm:ss` or `d:YYYY-MM-DD`), independent of the UTC hourly schedule key. The exact-post marker is rechecked after inference and immediately before sending, and cannot be bypassed with force. If a definite legacy slot collision or seen marker appears after the pending claim was committed but before any send began, authorized cleanup releases only that exact pending dispatch and preserves an `aborted-before-send` attempt audit. Any ownership/authorization loss, database cleanup failure or other unknown preflight failure conservatively retains the pending dispatch and blocks readiness, even when no sender call occurred; use audited `not-sent` resolution after independent inspection. Rejection, timeout or an ambiguous result never creates a false seen marker; a send/commit failure rolls the marker back with bookkeeping and preserves the pending dispatch for audited recovery.

This protocol is **not authorization to run Laravel and TS writers concurrently**. Laravel manual commands bypass the scheduling gate, slots expire, a slot boundary can race a running process, and expired cache rows may already have been garbage-collected. Absence of a recent key therefore cannot prove a writer is stopped, and a cache preflight cannot guarantee exactly-once network delivery. Existing stopped-writer, history-verification, operator approval and unresolved-dispatch rollback gates remain required. After an ambiguous send, do not resume Laravel merely because the shared slot expires; Laravel hourly delivery does not consult the TS uncertain table. Readiness remains a pending/uncertain-dispatch check, not independent proof of a stopped legacy process.

Four actual Opus reviews identified and corrected final seen checks, no-send abort cleanup, PHP title normalization and confirmed-send recovery interoperability.
