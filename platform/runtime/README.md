# TypeScript runtime and operator handoff

This is an isolated candidate runtime, not the active deployment. Build context is the repository root; the existing root Dockerfile and production Laravel services are unchanged.

```
cd platform
docker compose -f compose.yml -f compose.runtime.yml build web
docker compose -f compose.yml -f compose.runtime.yml up -d --wait web
```

The single web image runs Fastify on 8000 and Next standalone on loopback 3100. Fastify owns `/api/v1`, authenticated `/api/ops`, and the signed deployment relay; other presentation routes go to Next. API URLs therefore work on the public origin. The local overlay exposes 38000 on loopback. Use a reviewed Tailscale binding or forwarding arrangement for shared previews. The image has no application secret files, runs as `node` with `tini`, and constrains web heaps to 384 MB Next + 256 MB API inside the 1 GB container. Actual peak RSS still needs workload measurement.

`/up` is process liveness. `/runtime/ready` checks database readiness and the internal Next page. The worker uses this same immutable image with `node runtime/launcher.mjs worker`, health-checking its actual BullMQ Redis connection and active processor on loopback 8001. A child failure shuts down its peers. SIGTERM drains the API with 35-second container grace. The worker requests cooperative cancellation of source/AI calls and drains journal cleanup for up to 240 seconds; its launcher allows 250 seconds and the container requires at least 5 minutes. Worker is an opt-in Compose profile and intentionally fails closed with the default disabled ingestion gates. Do not interpret a running web container as a running scheduler.

## Operator API

Interactive editorial management uses Google administrator sessions with same-origin CSRF protection and individual audit identities. Production service-token authentication requires both an explicit `TS_OPS_SERVICE_AUTH_ENABLED=true` gate and a random `TS_OPS_TOKEN` of at least32 characters in runtime secrets; it is restricted to headless requests without Cookie, Origin or Sec-Fetch headers. Workflow/ingestion `/api/ops` endpoints remain token-only automation and do not inherit Google reader/admin access. An explicitly supplied Authorization header selects service-token handling, including when empty or invalid; it never falls back to a session. Responses are no-store and CORS is not enabled. Do not embed service tokens in browser bundles or public server-rendered data. Frontend-first production keeps service authentication and all execution gates off. See [accounts handoff](../docs/accounts-handoff.md) for Google Console registration, own account tables and human acceptance; account login does not grant workflow execution.

- `GET /api/ops/ingestion`: all 45 legacy workflow declarations plus new vocabulary workflows, actual implementation state, ownership/gates, and recurring configuration status.
- `GET /api/ops/ingestion/runs/:id`: durable vocabulary run status/page count and timestamps. A missing run is explicitly not evidence about queue state.
- `POST /api/ops/ingestion/preview`: validates `{workflow:"tags.vocabulary.sync",input:{id,window:{since,until},maxPages}}` without provider, DB, or queue writes. maxPages is 1–100.
- `POST /api/ops/ingestion/run`: enqueue that same supported vocabulary job only. Requires `TS_OPS_EXECUTION_ENABLED=true`, an exact `TS_OPS_WRITE_ALLOWLIST`, and all existing ingestion ownership/production/scheduler gates. Other registered workflows use the generalized operator API below. No request controls a shell command or environment.

The inventory is not a claim of full feature parity. A pending Laravel workflow cannot execute through this API. A queued job is not evidence it completed; the existing BullMQ job and durable vocabulary run record hold execution status.

## Deployment relay

`POST /ops/deploy/dokploy` is disabled unless `TS_DEPLOY_RELAY_ENABLED=true`, a 32+ character `DOKPLOY_DEPLOY_RELAY_SECRET`, secret `DOKPLOY_DEPLOY_WEBHOOK_URL`, and exact `TS_DEPLOY_REPOSITORY` are configured. Configure GitHub webhook content type as `application/json`. It validates the GitHub HMAC over raw bytes, push event, repository, main branch, and commit before issuing a bounded server-side request. The body has a 1 MiB cap. Redirects are rejected. Signed commit identity receives a Redis NX claim retained for 30 days, including failures/timeouts, because the upstream deploy may have been accepted. Inspect Dokploy before explicitly clearing an ambiguous claim; never blindly retry it. A 503 does not imply no deployment started. Redis persistence must remain enabled and private. Structured logs record claim hash, commit, and delivery without secret URLs. Like the existing Laravel relay, Dokploy builds current main HEAD, not a guaranteed pinned signed commit; verify the actual deployed image SHA. The signed commit deduplicates triggers, and a signed old payload may trigger a current-main rebuild after the 30-day retention. This relay requests the configured web deployment only; release automation must separately update the worker to the identical revision.

## Required production handoff

1. Complete route/job parity and captured-response comparisons. Review code, tests, quotas, notifications, provenance, freshness, and partial-run behavior. Record accepted gaps explicitly.
2. Create a database backup outside the repository and restore it into an isolated database. Record backup timestamp, schema version, restore result, and retention without secret material. Preserve the prior web and worker immutable image references and exported runtime configuration in protected storage.
3. Build and stage an immutable TS image by commit digest. Apply reviewed migrations using a dedicated operator task; no runtime container performs migrations at startup. These include new tables/indexes and existing-column type changes in migrations007/008, so review actual DDL and preserved-source fingerprints rather than assuming every change is additive. Public-report parity inspection uses a read-only DB account with login disabled. Account-enabled Web instead uses the per-table grants in [accounts handoff](../docs/accounts-handoff.md): SELECT-only on report sources, necessary DML only on its own account/reader tables, INSERT/SELECT-only audit and no DDL. These are distinct validation modes; do not grant source writes to enable login. Apply migration014 for bounded operator journal indexes; runtime needs SELECT on the four journal tables, never DDL. See [operator surface disposition](../docs/operator-surface-disposition.md). Load-test readiness, memory, SSR, and worker shutdown.
4. Obtain explicit per-workflow writer-transfer approval with exact `TS_INGESTION_OWNERS` and allowlists, including any external API quota usage. Disable/drain that Laravel workflow first, verify no overlapping process/lease, then enable its TS writer. Roll forward one workflow at a time. Keep notifications disabled until dedup/history migration is verified.
5. Route a staging hostname to the Fastify 8000 entrypoint and verify public pages, legacy redirects, API, RSS, auth, and source data. Switch the public route only after review. Web and worker must use the same immutable image digest, set the actual Dokploy/Swarm stop grace period to at least 35 seconds for web and 5 minutes for workers, and be independently redeployed/verified; a successful web deploy alone is insufficient.
6. Verify runtime process/image state, `/runtime/ready`, worker health, captured execution logs, source timestamps, and provider outcomes. For the approved account release, separately require `/auth/me enabled:true`, verified 012/013 schema/grants, working reader routes and the post-switch human Google acceptance window/rollback triggers in [accounts handoff](../docs/accounts-handoff.md). Preview login does not validate the production OAuth combination. Do not depend on Cloudflare headers as proof of revision.
7. Rollback: stop/drain affected TS workers and disable TS execution first; restore the previous web route/image and operator configuration. Verify exclusive ownership before re-enabling Laravel schedules. Keep additive schema during immediate rollback; restore data only through a separately reviewed maintenance plan if required. Never run both writers to catch up simultaneously.

No production domain, job gate, secret, database, webhook, or service was changed by adding this runtime.

Use the [release evidence sheet](../docs/release-evidence.md) to distinguish completed local checks from the deployment-specific evidence still required by these steps.

## Generalized reviewed workflow queue

The worker now dispatches the actual reviewed YouTube/AI CLI adapters and full-vocabulary/matching commands. `GET /api/ops/workflows` lists these registrations. `POST /api/ops/workflows/preview` and `/run` use `{workflow,id,input:{options:{...}}}`; options are validated without shell execution or caller-supplied environment. The preview is parameter validation, not a claim that sources are available. AI daily requires both `ai.daily` and `ai.channel` in ingestion ownership and operator allowlists. `youtube.comments.reset` remains an explicit repair action, not a recurring job.

`/ops/ingestion` provides a browser console for this API. Its token exists only in page memory; changing input invalidates the preview. Queue status can be read at `/api/ops/workflows/jobs/{queueId}` with authentication. Expired records report unobserved, never completed. Failures expose no raw driver/provider message. Source results include a durable `executionKey` for correlation with `ts_job_runs`.

CLI: `workflow:enqueue --job=youtube.videos.stats --id=EXPLICIT_RUN --input=FILE` validates only; adding `--execute` performs gated queue submission. FILE contains `{"options":{"limit":25}}`. Queued work never enables a gate or creates a recurring schedule. Same IDs bind immutable input with an atomic Redis digest; reusing an ID with different input returns409. Generic failed jobs need a separately identified reviewed retry; vocabulary window jobs retain their checkpoint retry behavior.

Queue input tombstones are retained without a TTL, independently of the 7-day/1000 completed and 30-day/1000 failed BullMQ record retention. If a tombstone remains but its job is missing (including an ambiguous enqueue failure), enqueue returns409; inspect the same queue/run identity and durable history first. A concurrent submission may still be completing, so do not create a different ID merely because this response was received. Keep Redis AOF persistence, backups and a no-eviction policy: loss of Redis tombstones invalidates deduplication guarantees and requires reconciliation before restarting producers. This is not a cross-datastore exactly-once guarantee. Do not delete tombstones merely to retry. BullMQ automatic stalled replay is disabled (`maxStalledCount:0`); interrupted work is recovered via explicit subsequent workflow runs and its durable journal. Retained completed submissions return200 with state, waiting/active submissions202, and previously failed/conflicting/unretained submissions409. Once an enqueue succeeds, a later status lookup failure returns202/unknown with its ID; an immediately failed new job reports200/failed. Vocabulary window retries are an explicit exception: they replay a pinned durable checkpoint, binding id/window while permitting a different page cap only while its failed BullMQ record is retained. After that record expires, use the explicitly gated vocabulary CLI to resume its durable checkpoint; the queue will not recreate an ambiguous run. Vocabulary enqueue/retry uses a bounded Redis submission lease to serialize failed-state page-cap updates; concurrent callers receive SUBMISSION_IN_PROGRESS and keep the same run ID. Current stored maxPages is returned, so completion never pretends to apply a new cap.

Worker startup requires at least one permitted workflow. Each dequeued job independently rechecks its exact owner, scheduler and production gates; unauthorized queued jobs fail before source access. `user-token` is the legacy AI result namespace identifier (for example `cli`), not an authentication credential.

Before **each** workflow ownership transfer, stop the corresponding Laravel scheduled entry and drain its in-flight processes, including daily/hourly pipeline dependencies and manual invocations. Verify the separate Laravel scheduler container has the changed configuration. Matching AI business locks and comment queue claims are defense in depth; they do not authorize overlapping writers. Laravel file-cache locks are not shared between containers. Never run Laravel and TS for the same workflow simultaneously, even while catching up. Reverse the stop/drain sequence during rollback.

## Required isolated integration lane

Start `docker compose up -d --wait db redis` in `platform/`, then run `npm run test:integration`. The lane fails if prerequisites are missing, enables every DB/Redis test flag, initializes only `127.0.0.1:23306/youtube_board_test_rewrite`, applies local migrations, and runs workspaces/files sequentially. It deliberately ignores runtime DB destinations and API credentials. Fresh Compose volumes create the test database via `tools/init-test-database.sql`; existing local volumes need that reviewed local initializer applied first. Redis tests use database14 and clean their own keys without FLUSH. The lane lock prevents two lane runners from colliding; do not run manual DB fixture suites concurrently. `npm test` remains the offline/unit lane and reports skipped integration tests explicitly.

Source-job production preflight also requires `TS_LARAVEL_LOCK_STORE=stopped` after the documented writer stop, or `TS_LARAVEL_LOCK_STORE=database` plus the **exact** non-secret `TS_LARAVEL_CACHE_PREFIX` of an explicitly configured Laravel database cache lock store. The latter shares `cache_locks` lease keys and renewal, and requires that existing Laravel table; it does not create it in production. Leave both unset until reviewed handoff. Current Laravel file-cache configuration cannot be treated as a cross-container lock. The stopped-writer handoff requirement still applies in database mode.

## Explicit recurring producer

`runtime/scheduler.ts` is a separate producer process; the worker only consumes. Copy the empty `runtime/schedules.example.json` to protected runtime configuration and add individually reviewed entries. The `scheduler` Compose profile mounts that configuration read-only and uses the same immutable image as web/worker. No configured entry or production gate is activated by this implementation. Numeric five-field cron expressions use **Asia/Taipei**. Unsupported syntax is rejected. A slot can be recovered within the default two-minute lookback; longer outages need an explicit bounded `scheduler:tick --lookback-minutes=N` (maximum60 and256runs) or workflow-specific catch-up. This prevents unbounded quota bursts after downtime.

Example entry (must be reviewed before activation):

```json
{"id":"video-stats-v1","workflow":"youtube.videos.stats","cron":"*/9 * * * *","options":{"limit":25}}
```

`window` may be `previous-hour` or `previous-day` for explicit `from`/`to` SQL timestamps, or `yesterday-date` for a date-only catch-up command. Manual reset/restore operations cannot recur. `ai.daily` with `missing-only:true` can fill missing conditions without regenerating completed output; source-first catch-up and hourly pipelines have additional source dependencies/gates. A queue success never proves those sources were complete.

Preview: `npm run start -w @youtube-board/jobs -- scheduler:tick --config=FILE --at=2032-01-01T00:00:00Z`. Add `--execute` only for gated queue submission. The daemon ticks every15seconds and is ready only after a recent successful Redis/config/gate tick. Each schedule-id+UTCminute receives a deterministic run ID, so overlapping producers/restarts use the same queue identity. Inputs are immutable within that ID; changing an entry's options needs a reviewed new schedule ID/version. Keep the same ID on ambiguous results and reconcile it first. Retained failed jobs are not implicitly replayed; later explicitly configured catch-up slots use durable workflow state. Runtime changes require scheduler reload/redeploy alongside the worker and web releases.

Ambiguous enqueue failures intentionally retain their tombstones forever and return `SUBMISSION_UNOBSERVED` with the derived queue ID. This sacrifices automatic recovery of that single submission in order to prevent a lost `queue.add` acknowledgment followed by retention from causing duplicate execution. Do not use a two-phase pending tombstone as permission to re-add: an accepted job may already have executed. After checking source/run history, an operator may authorize a new independently identified run, or a configured catch-up slot may reconcile durable state. A stored vocabulary page cap is the current retry request, not proof of the cap used by a previous attempt.

The recurring producer now opens a fresh bounded Redis connection per cycle, so a temporary restart does not strand it in ioredis `end` state. One failed queue submission does not prevent later slots from being attempted. Failed, ambiguous or unavailable results produce `schedule-attention` events with schedule, slot, run ID and queue ID when known, and fail readiness for that cycle. A fixed per-queue persistent UTC-minute watermark detects gaps exceeding the two-minute lookback. The missed interval is reported without automatically creating a quota burst; reconcile via the bounded preview/execute command. Attention events also enter a capped Redis stream (`youtube-board-ts:scheduler:attempted-minute:attention`, approximately1000entries); retain logs externally and alert on `schedule-attention`. A later healthy cycle may restore readiness, so readiness alone is not an unresolved-incident ledger.

The scheduler watermark means **attempted slots**, not successful jobs. It survives configuration changes and key reordering; all concurrent producers for this queue must use the same reviewed configuration. Stop/drain old producers before deploying a changed configuration. First startup logs `baseline:unobserved`, which makes no claim about time before installation. Audit-persistence failures and shutdown return partial run IDs in stdout and mark the cycle unhealthy; interrupted plans do not advance the watermark. Unresolved events require external log retention/alerting and reconciliation; readiness may subsequently recover. Keep producer clocks synchronized.

## Per-batch worker topology

Production runs one worker process per handoff batch (`shared/worker-batches.ts`: `cache`, `youtube-source`, `comments`, `ai-daily`, `ai-hourly`, `ai-mayor`, `telegram`). `tags.videos.match.recent` and `channels.avatars.refresh` belong to `cache`: they derive TS-owned data without quota and already share one host lock. Their `ts-worker.py` systemd timers stop at the batch-1 cutover, when scheduler entries replace them. The `cache` worker then needs the writable media volume.

- Facade: `WORKER_BATCH=<batch> node tools/worker-schema.mjs` previews one facade `youtube_board_ts_worker_<batch>` and one principal `youtube_ts_w_<batch>` (hyphens become underscores). The principal gets the table-level union of every profile in the batch, including declared dependencies such as `ai.daily` → `youtube.tag_videos.backfill`. `--execute` has the same backup/restore and new-principal requirements as single-workflow facades.
- Worker: `TS_WORKER_SCHEMA_MODE=facade`, `DB_DATABASE=youtube_board_ts_worker_<batch>`, `TS_WORKER_BATCH=<batch>` (no `TS_WORKER_WORKFLOW`; setting both is rejected). The worker consumes only `youtube-board-ts-batch-<batch>` with concurrency 1, so jobs run one at a time in arrival order. Example: the 9–10 cache jobs of a `27 3,…` slot run back to back instead of failing on the non-waiting writer lock. It refuses jobs outside its batch before any gate or source access. It starts only if at least one batch workflow passes the gates, and every job still rechecks owners, allowlist, production and scheduler gates.
- Producers (scheduler, `/api/ops/workflows/run`, CLI `workflow:enqueue`): set `TS_QUEUE_MODE=batch`. Each workflow is routed to its batch's queue. Workflows outside every batch (vocabulary sync, operator repairs) are refused in this mode. Run IDs, input tombstones and queue IDs are derived exactly as before. One scheduler serves all batches with the merged configuration of the active batch files (`runtime/schedules.batch*.json`). Its watermark key is `youtube-board-ts-batch-queues:scheduler:attempted-minute`. With `TS_WORKER_BATCH` set, a scheduler accepts only that batch's entries and uses that batch's watermark.
- Single-workflow facades (`TS_WORKER_WORKFLOW`, used by the `ts-worker.py` recent/quality/avatars timers) and `TS_QUEUE_MODE=workflow` keep their existing plans, queues and behaviour.


## Local backup and restore rehearsal

Run `npm run db:restore-drill` to preview, then `npm run db:restore-drill -- --execute` to rehearse against the isolated Compose preview database. The tool ignores runtime DB credentials, accepts only the fixed loopback development service, and refuses production mode. Stop local preview writers before execution: MyISAM consistency requires table locks during the dump. It restores into a newly created random database, compares every base table's engine, `SHOW CREATE TABLE` definition, column metadata, exact row hashes and trigger metadata, verifies the source snapshots before and after the drill match, and drops only the restore database it created. The source is never reseeded.

Private SQL and a non-secret hash manifest remain under ignored `.local/restore-drill/` with restricted file permissions. The latest 2026-10-12 local exercise matched 93 base tables, 10 triggers and 634 synthetic/preview rows, including table definitions and database charset/collation. The source's before/after fingerprints matched. This demonstrates the local procedure only; it is not a production backup or authorization to restore production. The production rehearsal in handoff step 2 still needs an approved export, isolated target and measured downtime/restore time. A separate [historical migration and response comparison](../docs/historical-parity.md) preserves 298,991 original rows across 14 TS migrations in isolated copies; neither exercise substitutes for the other.

The gateway forwards only GET/HEAD of the exact `/ops/ingestion` presentation page to Next; nested legacy ops mutation paths remain blocked. Credentials are stripped before forwarding presentation requests. `/manage/editorial` is likewise presentation only: all data changes go through separately authenticated, gated APIs. Channel adoption uses the standalone `youtube:channels:adopt` CLI; notification readiness/reconciliation use `notify:telegram:readiness` and `notify:telegram:resolve`. These manual maintenance commands cannot be scheduled through the queue registry.


Restore tooling pins the local Docker Unix socket, Compose file/project and environment, and verifies a random database connection lock through both loopback and container clients before dumping. Views, routines and events are explicitly rejected by this local drill; base tables, triggers and database charset/collation are compared. Failure diagnostics retain stage names and hashes, never raw rows, and cleanup failures name only the generated local target. Container-side timeouts bound dump/import processes. All presentation proxy requests are GET/HEAD only; authenticated mutations stay on the Fastify API. The console has no Next server actions or Pages Router data loaders.

An unobserved scheduler baseline and a future watermark both enter the attention stream and fail readiness for that cycle. Shutdown keeps an ambiguous submission's original state and lists every unattempted slot. Audit writes and watermark writes fail independently, preserving both queue IDs and attempted-time accounting. CLI `scheduler:tick --at` does not update the daemon watermark. The vocabulary retry submission lease is a best-effort serialization aid with bounded commands and repeated owner checks, not an atomic guarantee across process suspension. Attention may repeat per slot while within lookback; retain/deduplicate alerts externally rather than treating the bounded Redis stream as permanent incident history.
